# 默认设备改为稳定记录引用：修改方案

状态：已实施并通过主工作树自动化验证及独立复核。现行配置说明见 `docs/configuration.md`；本文保留实施设计与验收要求。真实设备、实网和旧版回退不在本次已验证范围内。

## 1. 目标与边界

让 `config.json` 只选择默认设备，让 `drives.json` 统一维护设备身份、协议地址和首选协议。

保持已确认的使用规则：

- 手动添加只输入 IP，通过发现取得真实服务地址，不猜扫描端口或路径。
- 首次确认双协议设备时默认 eSCL；用户保存的首选协议不被重新发现覆盖。
- CLI `--protocol` 只覆盖本次，不修改默认设备或首选协议。
- 连接失败不自动换设备、换协议或重新提交扫描任务。
- 只根据可靠身份信息跨协议合并。同 IP、型号或本地记录 ID 都不是身份确认依据。
- 旧 WSD / eSCL 地址配置继续可用。

本次不增加数据库、通用迁移框架、配置版本号、设备管理子命令或新的必填 CLI 参数。不修改扫描、PDF 和图像处理算法。

## 2. 配置和设备表的职责

| 数据 | 唯一维护位置 |
| --- | --- |
| 默认选中哪台设备 | `config.json` 的 `device.record_id` |
| 设备型号、协议身份、各协议地址 | `drives.json` |
| 用户首选协议 | `drives.json` 的 `preferred_protocol` |
| 本次协议覆盖 | CLI `--protocol`，仅存在于本次请求 |
| 扫描、输出和处理参数 | 继续使用 `config.json` 的原有分组 |

### 2.1 新配置格式

尚未选择设备时：

```json
{
  "device": {},
  "scan": {
    "dpi": 150,
    "mode": "color",
    "area": "a4",
    "timeout": "2m0s"
  }
}
```

选中设备后，程序写入如下引用。ID 仅为示例，不能复制后直接使用：

```json
{
  "device": {
    "record_id": "scanner_4e3bb8e859e34bd292ee7e65dd156413"
  }
}
```

`device` 可以省略。`device: {}` 表示没有默认设备，不表示主动发现网络。

`record_id` 模式不保存 `host`、`port`、`path`、`protocol` 或 `scheme`。若同一 `device` 对象显式混用两种格式，返回 `invalid_config`，不设置隐含优先级。

### 2.2 设备记录增加的字段

- `record_id`：本地记录的稳定主 ID。
- `record_aliases`：经可靠身份确认、合并进本记录的其他本地 ID，可省略。

示意记录：

```json
[
  {
    "record_id": "scanner_4e3bb8e859e34bd292ee7e65dd156413",
    "record_aliases": [
      "scanner_d0517944fe8e4ca99ec37915acb8f021"
    ],
    "id": "urn:uuid:12345678-1234-5678-9012-123456789abc",
    "model": "Example MFP",
    "protocol": "wsd",
    "preferred_protocol": "wsd",
    "endpoint": "http://192.168.1.8:8018/wsd/scan",
    "discovered": true,
    "verified": false
  }
]
```

此例只展示引用相关字段；双协议设备仍按现有格式保存 `endpoints` 和各协议身份。

现有 `id`、`capability_uuid`、`serial_number` 的含义不变。不得用 `record_id` 替换这些设备身份。

## 3. 本地记录 ID 的规则

### 3.1 生成与校验

- 使用标准库 `crypto/rand` 生成 128 位随机值，编码为 `scanner_` 加 32 位小写十六进制字符。不新增依赖。
- 只在持久化事务内为新记录或缺少 ID 的旧记录生成 ID。
- `loadDrives` 保持纯读取；不能每次读取生成不同 ID，也不能在 Agent 模式隐式写盘。
- 普通设备表写入顺便补齐旧记录 ID。TUI 打开旧设备列表时，可在同一设备表锁内执行一次补齐，再加载列表。
- 已有合法 ID 必须原样保留。校验主 ID 和别名格式，并检查同一个 ID 不能属于两条记录。
- 沿用设备表总大小和协议地址数量限制。超过限制时写入失败，保留原文件，不截断引用别名。

ID 是本机引用，不由 IP、协议 UUID、型号、序列号或列表顺序推导。

### 3.2 更新、合并与地址复用

| 情况 | 处理 |
| --- | --- |
| 切换首选协议、刷新能力或调整列表顺序 | 保持原 `record_id` |
| 可靠身份确认是同一设备，发现了新地址 | 保持原 ID，更新地址 |
| 两条已有记录经可靠身份确认可以合并 | 保留一个主 ID，其他主 ID 及别名并入 `record_aliases` |
| 同地址发现可靠身份冲突，按现有规则替换为另一设备 | 新设备必须使用新 ID；不继承旧 ID、别名或用户偏好，旧引用失效 |
| 身份信息不足 | 不通过 IP、本地 ID 或型号补造跨协议关联 |

合并时优先保留已有记录的主 ID，别名去重。主 ID 与任一别名都解析到同一条记录。

别名只在设备表内解析，不建立多级跳转，也不在每次合并时改写配置文件。这使设备合并只需原子更新一个文件。

若待合并记录都设置了用户首选协议且两者冲突，停止本次合并写入并提示用户统一偏好，不静默覆盖其中一项。

本次不扩展现有地址复用处理为设备历史档案系统；关键约束是旧默认引用绝不能被转交给另一台设备。

本地 ID 不是硬件认证，也不会自动发现设备的新 IP。地址更新仍依赖可靠身份确认。复用现有能力查询结果：若出现有效序列号或同协议、同来源能力 UUID 的明确冲突，返回 `device_identity_conflict`，不得更新原引用或提交扫描任务。不能把不同来源的 UUID 直接视为同一种身份比较。设备没有可比较身份时，不宣称已重新确认硬件身份，也不据此建立新的地址关联；此时仍受已有地址和设备发现能力限制。

## 4. 请求解析和界面行为

### 4.1 设备选择与协议选择分开

设备目标按以下顺序确定：

1. 用户显式传入的 CLI 地址参数。
2. 配置中的 `device.record_id`，或旧格式设备地址。
3. 无默认设备：TUI 打开设备列表；Agent 返回 `device_required`。

确定设备后，协议按以下顺序确定：

1. 本次显式 `--protocol`。
2. 该设备保存的首选协议。
3. 尚未设置用户偏好时，沿用当前初始选择规则。

只传 `--protocol` 不代表选择另一台设备。所选设备未确认支持该协议时直接报错。

### 4.2 引用和临时地址

- 默认引用支持主 ID 和别名；成功解析后，使用该记录当前首选入口。
- 引用不存在时返回 `device_record_not_found`，不退回 IP、型号或其他设备。
- TUI 对失效默认引用显示原因，允许用户主动打开设备列表重新选择；不自动选中其他设备并开始验证或扫描。
- 显式 `--host` 或 `--endpoint` 可以绕过一个格式合法但已失效的默认引用。配置语法错误或混用格式仍报配置错误。
- 新引用配置下，仅传 `--port` / `--path` / `--scheme` 而没有 `--host` 时，报告需提供明确地址；不隐式修改设备表中的连接参数。旧地址配置继续保留原有高级覆盖语义。

### 4.3 TUI 和普通文本选择

- TUI 内部用 `record_id` 追踪当前设备、列表选择和首选协议修改，不再把可变化的主 endpoint 当作设备主键。
- 屏幕仍显示型号、IP 和当前协议，使用当前深色／浅色前景色主题，不要求用户输入或记住记录 ID。
- 从列表选用或手动添加后，先只读验证，再取得已持久化记录的 ID，最后保存默认引用。
- `--protocol` 覆盖只用于本次验证和扫描，保存默认引用时不附带协议地址。
- 设备表注册路径需要返回落盘后的记录 ID，避免保存后再凭 IP 查找并误认另一条记录。

### 4.4 Agent 模式

- 可读取并使用现有主 ID 或别名；不生成 ID、不迁移文件、不修改偏好。
- `discover` 只在结果与一条已保存记录唯一匹配时，附带已有的 `record_id`。
- 新发现设备或尚未补齐 ID 的旧记录可以没有 `record_id`。不能为使输出完整而隐式写盘或返回临时随机 ID。
- 多条已保存记录匹配同一发现结果时，不任意选一个 ID。合并需要普通模式的持久化流程。
- 保持单个 JSON 结果和既有取消、超时约定；新错误码写入接口文档。

## 5. 旧格式兼容和渐进迁移

继续接受原有地址配置，例如：

```json
{
  "device": {
    "host": "192.168.1.8",
    "port": 8018,
    "path": "/wsd/scan"
  }
}
```

旧 eSCL 的 `protocol`、`scheme` 也继续接受。旧端口、路径和协议默认值只在兼容分支应用，不能污染新引用模式。

迁移策略：

1. 读取旧配置本身不改写文件。旧配置可以继续运行，不要求一次性迁移。
2. 用户在 TUI 或普通文本流程明确选择设备、验证成功并保存默认设备时，改为写入 `record_id`。
3. 默认选择的登记发生在验证之后、开始扫描之前；普通文本旧流程中先保存后验证的顺序也要同步修正。
4. 普通 `info` 可以更新设备记录，但不因此自动改写旧配置中的默认选择；Agent 始终不迁移。
5. 重新读取最新配置，仅替换 `device`，保留其他配置分组。自动补齐 ID 只作用于设备表，不顺带改变默认设备。
6. 不凭“配置 IP 与某条记录 IP 相同”自动绑定。地址和身份存在歧义时，要求用户确认设备。

旧格式的 `protocol` 用于解释旧地址，不自动转换成设备表中的用户首选协议。

## 6. 写入顺序和失败处理

复用现有设备表锁、文件大小校验、同目录临时文件、同步、原子替换和 `0600` 权限；保留符号链接拒绝和取消检查。

默认设备登记顺序固定为：

1. 只读验证设备。
2. 在设备表锁内注册或更新设备，补齐 ID，成功写入 `drives.json`，返回记录 ID。
3. 确认引用仍有效，重新读取配置，原子保存 `device.record_id`。
4. 全部成功后才允许进入后续扫描流程。

不宣称两个文件构成原子事务：

| 失败点 | 保留状态 |
| --- | --- |
| 验证失败或取消 | 默认配置不变，不创建扫描任务 |
| 设备表写入失败 | 默认配置不变，不写入悬空新引用 |
| 设备表成功、配置写入失败 | 保留设备记录，原默认配置不变，报告保存失败，不继续扫描 |
| 两次写入之间进程退出 | 可能多出已登记记录，但原默认配置仍可读 |
| 合并两条已引用记录 | 仅改设备表并保留别名，原配置引用仍可解析 |
| 记录被并发替换或删除 | 旧引用明确失效，不改指其他设备 |

不为配置写入失败回滚已经分配的设备 ID。引用不应在失败重试后重新指向另一台设备。

### 7.1 配置文档清理规则

配置主文按当前规则重写，不在旧正文后不断追加补丁说明。新格式说明与实现同批交付，不能提前把未实现格式写成当前可用配置。

`docs/configuration.md` 只保留四类内容：

1. 配置文件位置、创建方法和一份当前完整示例。
2. 当前推荐字段表，包括 `device.record_id`、扫描、输出和处理参数。
3. 默认设备、首选协议与本次 CLI 覆盖之间的简明优先级。
4. 直接相关的配置错误处理，以及指向专题文档的必要链接。

清理时区分以下情况：

- **已失效或被替代的行为：直接删除。** 包括自动协议 fallback、普通用户填写扫描端口和路径、把 WSD 固定地址当作通用默认、新流程仍保存完整设备地址等说明。
- **仍受支持的旧格式：集中迁出。** `device.host`、`port`、`path`、`protocol`、`scheme` 的旧配置语义只在 `docs/configuration-compatibility.md` 说明。主文不列入推荐字段表，只在末尾保留一个兼容入口。
- **其他专题已有的说明：引用而非复制。** 扫描仪协议、证书和身份细节归 `docs/escl.md`；TUI 操作和 Agent 输出归 `docs/interfaces.md`；构建及安装要求归各自文档。主配置文档不再重复整段教程。
- **历史过程：不放入用户配置指南。** 不按旧版本再建一组配置文档，不保留失效示例作历史纪念；需要追溯时使用 Git 历史。实施完成后更新本方案状态，不将其混入普通使用入口。

`config.example.json` 与主文完整示例保持一致。README 和帮助中的配置示例同步更新，不能留下另一套推荐格式。旧格式读取兼容保留；文档精简不等于移除兼容代码。

## 8. 实施顺序

1. **记录层**：增加 ID 和别名，验证生成、持久化、合并和身份冲突规则。
2. **配置层**：支持引用与旧格式，明确互斥和默认值边界。
3. **请求层**：接通引用解析、显式地址覆盖和 Agent 只读路径。
4. **选择与保存层**：接通 TUI、文本选择及验证后登记；首选协议按 ID 修改。
5. **示例与文档**：重写精简配置主文，替换主示例，集中旧格式兼容说明，删除失效及重复段落，补齐发布白名单、链接、错误码和回退限制。
6. **完整回归**：执行测试、vet、构建和 npm 检查；再决定是否开展真实设备验收。

每步先通过针对性测试；不自动提交、推送、发布、安装依赖或修改用户实际配置。

## 9. 验收标准

至少覆盖以下情况：

- 旧 WSD / eSCL 配置可读；新引用配置可读；混合格式、非法 ID、重复 ID 和跨记录别名冲突被拒绝。
- 同一记录经重新读取、能力刷新、地址更新和协议切换后 ID 不变。
- 两个旧 ID 合并后都能解析；别名不形成跳转链。
- 地址被不同身份设备复用时，新设备不继承旧 ID、别名或偏好；能力查询出现可比较身份的明确冲突时，保存默认引用和扫描创建 POST 都被阻止。
- 首选协议冲突不被静默覆盖；CLI 协议覆盖不改变持久化默认。
- 无默认引用、失效引用、显式 IP 覆盖失效引用，以及同 IP 多身份设备的行为符合第 4 节。
- 旧设备表补齐 ID 后可稳定重读；纯读取和 Agent 不修改任一配置文件。
- TUI 和文本选择都先验证后保存；验证或保存失败不开始扫描。
- 设备表写入失败、配置写入失败、取消、迟到结果和并发更新不造成错误绑定或配置损坏。
- 首选协议失败时没有其他协议请求；扫描创建 POST 不因迁移或解析重试。
- 伪终端窄屏、当前协议文字和 `NO_COLOR` 行为保持有效；主题仅指定前景色，`NO_COLOR` 下不输出颜色。
- 使用隔离 `HOME` 完成测试，不操作真实用户配置。
- 主配置文档、示例文件、README 和帮助只推荐新格式；主文不残留旧地址字段表或失效行为。
- 必要旧格式说明只有一份，主文只提供一个入口；专题间链接有效，新增文档包含在发布包中。

最终检查：Go 全量 race 测试、`go vet ./...`、构建、`node --test npm/package.test.cjs`、`git diff --check`。环境条件跳过的测试单独报告。

## 10. 回退和未验证项

增加本地字段后，旧版本可能因严格 JSON 字段校验而拒绝新配置或新设备表。因此，回退旧程序时不能只替换二进制，还需要恢复匹配的配置和设备表备份。实际升级前再按授权备份用户文件；不在本轮读取或迁移真实配置。
